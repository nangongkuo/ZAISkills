# ACS Develop Review

## Goal

回顾一次完整的研发过程，识别开发中犯过的错误、走过的弯路、反复修改的地方，将这些经验教训提炼为符合 acs-knowledge-scanner 格式的 Knowledge 文档，帮助后续 AI 和开发者不再犯同样的错误。

核心原则：只沉淀真正能改变后续开发决策的经验，不写泛泛的总结。

## Inputs

技能启动后，通过交互式对话引导用户逐步输入以下信息：

**步骤 1： 确认回顾范围**
- 告知用户将回溯当前会话的完整对话历史
- 询问用户本次开发的仓库路径（默认取当前工作目录）
- 等待用户确认后继续

**步骤 2： 确认输出位置**
- 询问用户知识文档要写入的目标路径
- 说明默认路径为 `<repo>/knowledge/review/<doc-name>.md`
- 等待用户确认后继续

## Workflow

### 1. 回溯对话历史，收集研发过程信息

**核心信息源是当前会话的对话历史。** 开发者使用 Claude Code 完成需求的过程中，所有的尝试、错误、修正、来回迭代都记录在对话里。

回溯整个对话，提取以下信号：

**a) 错误与修正**
- 用户纠正了模型的实现（“不对”、“改回去”、“不是这样”、“用错了”）
- 模型自己发现并修复了之前的错误（“抱歉”、“修正”、编译失败后的修改）
- 同一段代码被反复编辑（说明第一次没写对）
- 用户提供了额外的上下文才让模型走上正路（说明初始知识不足）

**b) 弯路与浪费**
- 先写了一段代码后又删掉，换了另一种方案
- 尝试了一种方法失败后切换到另一种
- 编译/测试反复失败后才找到正确做法
- 用户主动指出“项目里已经有现成的”

**c) 知识缺口**
- 模型不知道项目的某个约定或封装，导致走了弯路
- 模型不了解某个 API 的正确用法
- 模型对项目架构/模块边界理解有误

**d) Git 历史辅助（可选）**
- 如有需要，可运行 `git log` 和 `git diff` 辅助确认对话中涉及的变更
- 但对话历史是主要信息源，git 只是补充验证

### 2. 识别错误模式

对收集到的信息进行分析，识别以下类型的错误：

| 错误类型 | 对话中的识别信号 | 示例 |
| --- | --- | --- |
| API 误用 | 用户纠正了 API 调用方式、或编译失败后修改了调用 | 直接调了原生 API 而不是项目封装 |
| 架构理解偏差 | 代码被要求移到另一个模块、或用户解释了正确的层级关系 | 把代码放错了模块/层级 |
| 编译错误 | 对话中出现编译失败 → 修复的循环 | 类型不匹配、缺少依赖、import 错误 |
| 遗漏边界条件 | 用户指出需要补充判空/异常处理、或测试失败暴露了边界 | 忘记处理 null case |
| 重复造轮子 | 用户指出项目里已有现成封装 | 项目里已有 util 但模型又写了一个 |
| 规范违反 | 用户要求调整命名、结构、风格 | 不符合项目命名规范或目录规范 |

对每个识别到的错误，记录：
- **什么错了**：具体的错误描述
- **错误根因**：为什么会犯这个错（缺少知识、理解偏差、疏忽等）
- **如何修正的**：最终的正确做法
- **对话证据**：对话中哪个环节体现了这个错误和修正

### 3. 筛选值得沉淀的经验

不是所有错误都值得写成知识文档。只沉淀满足以下条件的经验：

**值得沉淀：**
- 错误的根因是“不知道项目有某个约定或封装”
- 这个错误其他开发者（或 AI）也很可能犯
- 知道正确做法后，可以直接避免

**不值得沉淀：**
- 纯粹的 typo 或手误
- 一次性的环境配置问题
- 已经在项目文档中明确说明的规范
- 过于特殊、不具有普遍性的边界 case

### 4. 向用户确认发现

将识别到的错误和筛选结果展示给用户：

```
## 本次开发回顾

### 识别到的问题

1. **[问题标题]**
   - 错误：[具体描述]
   - 根因：[为什么犯错]
   - 正确做法：[应该怎么做]
   - 证据：[对话中的哪个环节 / 文件路径]

2. ...

### 建议沉淀的知识

- [知识点 1]：[一句话说明]
- [知识点 2]：[一句话说明]

### 不建议沉淀的问题（仅供参考）

- [问题 X]：[原因：太特殊 / 已有文档 / ...]
```

等待用户确认：
- 哪些知识点需要沉淀
- 是否有遗漏的问题需要补充
- 输出文档名（kebab-case，不需要 .md 后缀）

### 5. 生成知识文档

对用户确认的每个知识点，生成一个符合 acs-knowledge-scanner 格式的 feature 文档。

文档格式严格遵循 [review-knowledge-template.md](...)。

关键写作原则：
- 把“错误经验”转化为“正向指引”——不要写“我犯了什么错”，而是写“应该怎么做、不要怎么做”
- 保持高信息密度，像速查卡一样
- Evidence 中使用对话中的关键信息和文件路径作为证据
- 全文控制在 150-300 字

### 6. 写入文件

将知识文档写入用户确认的目标路径。

写入完成后，向用户汇报：
- 每个文档的最终落盘路径
- 每个文档的核心内容摘要（一句话）

## Quality Bar

知识文档只有满足以下条件才写入：

- 错误根因是明确的（不是“可能”、“也许”）
- 正确做法是被验证过的（对话中最终确认了正确方案）
- 对后续开发者有实际指导价值
- 不与已有 knowledge 文档重复

如果本次开发没有发现值得沉淀的错误，直接告知用户“本次开发过程顺利，未发现需要沉淀的经验教训”，不要强行产出低质量文档。

## Output Rules

- 一个错误/经验对应一个知识文档，不混写
- 文件名使用 kebab-case
- 沿用 acs-knowledge-scanner 的 feature 格式，frontmatter 包含 `meta.name`、`meta.description`、`meta.keywords`
- 每个文档必须包含完整的 frontmatter
- 正文不超过 12 行有效内容
- 不贴大段代码，只摘关键方法名或路径

## Workspace Rules

- 主要信息源是当前会话的对话历史，不依赖外部 state 文件
- 可选使用 git history 辅助验证，但不做任何 git 修改操作
- 输出路径需经用户确认后才写入
