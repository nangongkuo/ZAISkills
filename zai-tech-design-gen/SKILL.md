# 系分文档生成

**核心目标**: 输入产品 PRD(语雀链接) + 目标仓库, 从零生成一份**经代码验证、对抗式自审**的系分文档。

**准确性三大支柱**:
1. **代码验证 + 反幻觉**: 分析过程中所有代码引用经 `grep`/`test -f` 验证存在, 方案结论基于已验证的代码分析, 而非臆测。
2. **PRD→代码定位引擎**: 跨越产品语言↔技术语言语义鸿沟, 见 `references/prd-code-locator.md`; 并行佐以 commit **历史变更信号**(上次类似需求改了哪些文件), 见 `references/commit-history-locator.md`。
3. **对抗式自审 + 人工检查点(HITL)**: 关键阶段必须停下等人确认——需求拆解、代码锚定、风险标记三处设置卡点, 人不放行不往下走。对抗式自审见 `references/adversarial-review.md`。

**设计原则**: 先用结构化高信号锚点(知识索引、原样文案、路由)定位, 最后才退化到模糊语义搜索, 全程不编造。

---

## 输入

| 参数 | 必填 | 说明 |
|------|------|------|
| prd_url | ✅ | 产品 PRD 地址(语雀链接) |
| repo_path | ✅ | 目标仓库绝对路径, 默认当前仓库 |
| branch_name | ❌ | 分支名, 不存在则回退 master/main |
| template_url | ❌ | 覆盖默认系分模板的语雀链接(不使用内置模板) |

---

## Workflow

### 阶段 0 - 输入收集

1. 提取 PRD 语雀链接: `yuque resolve <prd_url> --json` → `yuque show doc --id <id> --json`, 记录 prd_url（原始链接, 供系分文档头溯源）, prd_title, prd_body。
2. 确认目标仓库 (AskUserQuestion): 当前仓库（推荐）/ 本地路径 / SSH URL (clone 到 `.acs-tmp/tech-design-gen-<repo>/`)。验证 `.git` 存在。
3. 确认分支 (AskUserQuestion): 当前分支（推荐）/ 指定分支。指定分支不存在则回退 master/main 并告知。
4. **可选**: 询问是否传入覆盖默认的语雀链接 (template_url)，不传则用 `references/spec-template.md`。

失败处理: URL 无法解析→提示检查重试；读取失败→重试一次，仍失败提示提供本地文件。

### 阶段 1 - 知识准备

复用 sdd-coding 知识准备流程:
1. 检查 CLI: `which acs-knowledge-index`, 未找到→警告并进入降级模式（无知识匹配）。
2. 生成索引: `acs-knowledge-index setup <repo_path> --platform auto --output <repo_path>/knowledge/knowledge-index.json`。
3. Repo Overview 冷启动: `knowledge/project/_repo-overview.md` 不存在则快速扫描仓库生成。
4. 加载 `knowledge-index.json`: 获取全部知识文档 Meta; 分离 `_repo-overview.md` 作为全局上下文。

失败降级: sync/scan/overview 任一失败→警告并继续。

### 阶段 2 - PRD 结构化拆解

按 `prompts/prd-decompose.md` 的原则与 Schema, 把 PRD 正文拆成**原子需求点清单**。每个需求点含: id、做什么、功能场景、技术领域关键词、UI文案、涉及字段。

#### 👇 Checkpoint - 需求拆解确认

**必须停下等用户确认后才进入阶段 3。**

以表格形式向用户展示完整的原子需求点清单, 用 `AskUserQuestion` 请用户确认:
- 是否有**拆多**（一个需求被错误拆成多个）或**拆漏**（PRD 里有但清单里没有）的情况
- 每个需求点的**技术领域关键词**是否准确（关键词质量直接决定阶段 3 的 grep 命中率）
- 用户可以在此处补充关键词、修正分类、增删需求点

用户确认后, 将修正后的清单作为阶段 3 的输入。

### 阶段 3 - 仓库深度分析(代码锚定)

对**每个原子需求点**执行 `references/prd-code-locator.md` 定义的定位协议, 收集定位结果（入口/调用链/约束/置信度）。
- 所有代码引用经 `test -f`/`grep` 验证存在。
- 关键改动点追 1-2 跳调用链；复杂则阻断。
- 未定位的需求点标注 `[未定位到现有代码——可能是全新模块]`, 不编造。

**并行**: 对每个需求点同时执行 `references/commit-history-locator.md` 的 commit 历史定位通道, 产出「历史参照」对象（匹配 commit + 高频改动文件, 按 `test -f` 验证）。该通道**辅助增强**命中提升置信、补全漏区间；若空**不影响**识别为未定位（仍由五层锚点层决定），涉密/非 git 仓库 / 无历史 / 浅克隆无历史 → 该通道跳过并告知, 不阻主流程。

**启发**: 对每个**已命中**需求点执行 `references/pattern-learner.md` 的模式参照协议, 从入口文件的同目录/同基类/同路由中发现同类实现, 提取实现骨架（入口方法、依赖注入、数据结构等）, 作为阶段 5 生成“实现思路”的具体参照。该步骤为**增强项**——有参照则丰富方案（从泛写变成“照 X 类的模式”）, 无参照不影响主流程。

#### 👇 Checkpoint - 代码锚定结果审查

**必须停下等用户确认后才进入阶段 4，这是整个流程中最关键的人工检查点。**

将所有需求点的定位结果以表格形式展示给用户:

```
| 需求点 | 定位状态 | 锚点来源 | 涉及模块 | 历史参照佐证 | 架构模式参照 |
| R-01 | ✅ 命中 | 知识索引 | 登录模块 | 3 commits 同向 | 认证模块(同目录) |
| R-02 | ⚠️ 部分命中 | 术语grep | 鉴权服务 | 无 | Token管理(同基类) |
| R-03 | ❌ 未定位 | - | - | 1 commit 线索 | - |
```

用 `AskUserQuestion` 请用户逐项审查, 用户可以做 3 种操作:
- **确认**: 该需求点定位正确, 放行
- **纠正**: 告诉某个正确的模块/组件归属 → 模型验证后重新定位结果
- **补充**: 对未定位项提供线索（如“这块逻辑在 XXModule 里”）→ 模型基于线索在该模块范围内重新定位

用户全部确认后, 将修正后的定位结果作为后续阶段的输入。




### 阶段 4 - 歧义扫描 + 批量反问

1. 扫描“无法从 PRD + 代码推断”的歧义点（边界条件、异常处理、数据来源、影响方案走向的选择）。
2. 集中**一次** AskUserQuestion 抛出关键问题（最多 4 个）。
3. 次要歧义不打断, 留待生成时标注 `[假设]`。
4. 用户答完进入生成。

### 阶段 5 - 系分生成

1. 选模板: template_url（用户覆盖）> `references/spec-template.md`（默认）。
2. 按模板章节生成, 遵循 spec-template 的“填充规则”: **每个技术方案点必须基于已验证的代码分析，描述模块职责、数据流向和关键设计决策**。
3. 有模式参照的需求点, 方案设计应参照仓库中同类模块的架构模式来写，而非泛泛描述。
4. 未定位需求点在方案中显式标注, 不写成已确定。

### 阶段 6 - 对抗式自审

按 `references/adversarial-review.md` 切换“挑刺”视角复查初稿: 标记 `[假设]`/`[低置信度]`/`[需对齐]`/`[待确认]`, 重验声称“已验证”的引用, 汇总进第 8 章。

#### 👇 Checkpoint - 风险项确认

**如果对抗式自审产出了任何 `[假设]`/`[低置信度]`/`[需对齐]`/`[待确认]` 标记，必须停下等用户确认。**

将所有风险标记集中展示给用户, 用 `AskUserQuestion` 请用户逐项裁定:
- `[假设]`: 保留是否成立? 用户给出明确答案后更新系分内容
- `[低置信度]`: 方案是否采纳? 用户可确认或给出替代方案
- `[需对齐]`: 给出明确答案消除分歧
- `[待确认]`: 补充信息

如果对抗式自审**无任何风险标记**（全部引用验证通过、无假设/歧义），则跳过此 checkpoint 直接进入阶段 7。

用户全部裁定后, 将裁定结果合入系分文档。

### 阶段 7 - 确认与输出

1. 展示生成摘要: 需求点数、定位命中率、关联知识文档、人工审查修正项。
2. 输出方式 (AskUserQuestion): 写回语雀 (`yuque update doc --id <id> --body <content>`) / 保存本地 (`<repo_path>/.acs-tmp/tech-design-gen.md`)。写回失败→降级本地。
3. 引导: 提示可用 `/acs-junior-engineer` 启动编码工作流。
4. 清理: 若 clone 了临时仓库则 `rm -rf` 之。

## Error Handling

| 错误 | 处理 |
|------|------|
| 语雀 URL 无法解析 | 提示检查链接, 重试 |
| PRD 文档读取失败 | 重试一次, 仍失败提示提供本地文件 |
| 仓库路径不存在 / 非 git | 报错, 重新询问 |
| 分支不存在 | 回退到 master/main, 告知用户 |
| acs-knowledge-index 未安装 | 警告, 降级模式（定位退化到 grep 层） |
| 知识索引 / overview 生成失败 | 警告, 继续 |
| 需求点全部未定位 | 不终止: 系分整体标注风险, 在阶段 3 checkpoint 交由用户补充线索 |
| 文档写回语雀失败 | 降级为本地文件保存 |

## Workspace Rules

- 分析阶段对目标仓库**只读**，不修改源代码。
- 除阶段 0 的分支切换外，不执行修改仓库的 git 操作。
- 临时文件仅写入 `.acs-tmp/`。
- 输出经用户确认后才写入。
- clone 的临时仓库在结束时清理。

## Quality Bar

| # | 检查项 | 要求 |
|---|--------|------|
| 1 | 代码分析真实性 | 分析过程中引用的文件经 `test -f` 验证，类/方法经 grep 验证 |
| 2 | 需求覆盖 | 每个原子需求点都有定位结果（命中/部分/明确标注未定位） |
| 3 | 技术方案可信度 | 每个技术方案章节基于已验证的代码分析，或明确标注 `[未定位]` |
| 4 | 知识对齐 | 知识索引存在时，方案不与 Avoid 冲突；未用 Preferred Entry 时给出说明 |
| 5 | 人工检查点覆盖 | 阶段 2/3/6 的 checkpoint 全部经用户确认执行 |

达不到时: 明确告知未通过项, 在对应 checkpoint 交由用户裁定后继续。

> 注: 「历史参照」和「模式参照」均为**增强项**——命中提升方案质量，落空**不计入**质量不达标，不设硬门槛。
