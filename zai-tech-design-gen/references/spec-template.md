# 默认系分模板 (spec-template)

> 主流程阶段 5 使用, 用户传入覆盖模板(template_url)时, 读取其章节结构作为骨架替换本模板,
> 但仍按本文件的"填充规则"注入代码锚定内容.

## 模板章节

```markdown
# {需求名称} 系分文档

> 原始 PRD: {prd_url}

## 1. 背景与目标
{来自 PRD 的背景}
> 仓库技术栈上下文(来自 _repo-overview.md): {技术栈/架构分层}

## 2. 需求拆解
| 编号 | 做什么 | 功能场景 | 定位状态 | 置信度 |
|------|--------|----------|----------|--------|
| R1 | ... | ... | 命中/部分/未定位 | 高/中/低 |

## 3. 技术方案
### R1 {需求点标题}
- **涉及模块**: {模块名称及职责}（基于代码分析验证）
- **数据流向**: {数据从哪来、经过什么处理、到哪去}
- **关键设计决策**: {为什么这样做、备选方案及取舍}
- **约束**: {来自知识文档的 Avoid / Preferred}
- **历史参照**: {仓库中同类需求的实现模式}  ← 无历史命中则整行省略，不留空占位

## 4. 数据模型
- 模型结构: {实体名称 + 字段 + 类型 + 含义}
- 序列化模式: {Codable / Serializable / ...}
- 新增/变更字段: {字段 + 类型 + 变更原因}

## 5. 接口定义
- 遵循现有 API 风格: {命名/参数/返回 约定,附现有例子引用}
- 新增/变更接口: {签名}

## 6. 影响面分析
| 改动点 | 调用方 | 涉及范围 | 风险 |
|--------|--------|----------|------|
| {类/方法} | {谁调用} | {影响} | {风险} |

## 7. 测试要点
- 测试框架: {框架}
- 需覆盖场景: {场景清单}

## 8. 风险与待确认项
{对抗式自审产物汇总}
- `[假设]`: {推断项}
- `[低置信度]`: {未充分验证项}
- `[需对齐]`: {与架构/知识约束冲突项}
- `[待确认]`: {PRD 未覆盖、反问未问到项}
- **整体置信度评级**: 高 / 中 / 低
```

## 填充规则

| 章节 | 填充来源 | 硬要求 |
|------|----------|--------|
| 文档头 PRD 链接 | 阶段 0 的 prd_url | **原样填入阶段 0 收到的 PRD 源链接(非元数据)** |
| 1 背景与目标 | PRD + _repo-overview.md | --- |
| 2 需求拆解 | 阶段 2 原子需求点清单 | 每个需求点一行, 带定位状态 |
| 3 技术方案 | 阶段 3 定位结果 | **每个技术方案点必须基于已验证的代码分析, 描述模块职责、数据流向和关键设计决策, 或明确标注【未定位】** |
| 3 历史参照 | 阶段 3 commit 历史定位通道 | **增强项:有命中才写, 落空则整行不出现; 绝不为凑格式编造 commit** |
| 3 架构模式参照 | 阶段 3 pattern-learner 协议 | **增强项:有参照才写, 无参照整行不出现** |
| 4 数据模型 | 代码发现的 Model | 描述模型结构、字段含义、序列化方式 |
| 5 接口定义 | 代码发现的 API 风格 | 附现有 API 例子引用 |
| 6 影响面分析 | 调用链分析 | 关键改动点必填 |
| 7 测试要点 | 仓库测试模式 | 测试框架和覆盖场景 |
| 8 风险与待确认项 | 阶段 6 对抗式自审 | 所有假设/未验证项显式标注 |
