# 系分文档增强

**核心目标**: 以目标仓库的知识体系和既有代码为背景，深度理解需求，补全系分文档中对 SDD 流程关键的细节，最大程度提升 `acs-sdd-coding` 的编码准确度。

**增强维度**:
- 补充具体的文件路径、类名、方法引用
- 关联匹配的知识文档（knowledge）
- 基于仓库现有模式给出具体实现建议
- 补全缺失的接入方式、错误处理、边界场景

**设计原则**: 增强而非重写——保留原文档结构，在每个章节内注入增强内容，SDD 流程和人类均可消费。

---

## 输入

| 参数 | 必填 | 说明 |
|------|------|------|
| yuque_url | ✅ | 系分文档地址（语雀链接） |
| repo_path | ✅ | 仓库绝对路径，默认当前仓库 |
| branch_name | ❌ | 分支名，不存在则回退到 master/main |

---

## Workflow

### Step 1: 收集系分文档地址

询问用户系分文档的语雀 URL。

**执行**:

```
1. 接收用户输入的语雀 URL
2. yuque resolve <url> --json → 获取 doc_id, slug, title
3. yuque show doc --id <id> --json → 读取完整文档内容（body 字段为 Markdown）
4. 记录 doc_id, doc_slug, doc_title, doc_body
```

**失败处理**:
- URL 无法解析 → 提示用户检查链接后重试
- 文档读取失败 → 重试一次，仍失败则提示用户提供本地文件路径作为备选

---

### Step 2: 确认目标仓库

使用 AskUserQuestion 询问目标仓库来源:

| 选项 | 说明 |
|------|------|
| **当前仓库**（推荐） | 使用当前工作目录 |
| **输入本地路径** | 手动输入本地仓库绝对路径 |
| **输入仓库 SSH/URL** | clone 到临时目录 `.acs-tmp/tech-design-<repo-name>/` |

**验证**:
- 检查路径下是否存在 `.git` 目录
- SSH/URL 方式: `git clone --depth 1 "<url>" "<临时目录>"`
- 路径不存在或非 git 仓库 → 报错，重新询问

---

### Step 3: 确认分支

使用 AskUserQuestion 询问目标分支:

| 选项 | 说明 |
|------|------|
| **当前分支**（推荐） | 使用仓库当前 checkout 的分支 |
| **输入分支名** | 指定其他分支 |

**执行**:
```
if 用户指定分支名:
  git rev-parse --verify <branch_name>
  存在 → git checkout <branch_name>
  不存在 → 回退到 master（或 main），告知用户
```

---

### Step 4: 知识准备

复用 `acs-sdd-coding` 阶段 1 的知识准备流程。

**4a. CLI 检查**:

```bash
which acs-knowledge-index
```

未找到 → 警告用户，继续执行（降级模式、无知识匹配）。

**4b. 知识索引生成**:

```bash
acs-knowledge-index setup <repo_path> \
  --platform auto \
  --output <repo_path>/knowledge/knowledge-index.json
```

内部流程: 同步远程知识 → 配置 `.gitignore` → 生成知识索引 → 部署 OpenSpec Schema。

**4c. Repo Overview 冷启动检查**:

```
if <repo_path>/knowledge/project/_repo-overview.md 不存在:
  快速扫描仓库（根目录文件、2-3 层目录结构、3-5 个关键代码文件）
  按模板生成 _repo-overview.md
  写入 <repo_path>/knowledge/project/_repo-overview.md
else:
  跳过
```

**4d. 加载知识索引**:

读取 `knowledge-index.json`，获取全部知识文档的 Meta 信息（id, title, description, keywords, path）。将 `_repo-overview.md` 分离出来作为全局上下文。

**失败降级**:
- sync 失败 → 继续执行（使用本地知识）
- scan 失败 → 警告，继续执行（无知识匹配）
- overview 生成失败 → 继续执行

---

### Step 5: 文档解析与需求理解

**5a. 解析文档结构**:
- 识别所有章节标题（H1/H2/H3）和层级关系
- 提取每个章节的内容
- 构建 section_map: `[{title, level, content}, ...]`

**5b. 提取实现意图**:

从系分文档中提取以下信息:
- 新增的功能/能力
- 需要修改的现有模块
- 定义或变更的 API/接口
- 数据模型和数据流
- 涉及的技术领域关键词（用于后续知识匹配和代码搜索）

---

### Step 6: 输入质量门

基于 Step 5 的解析结果，检查系分文档是否满足增强的最低质量要求。质量不达标时直接打回，避免在低质量输入上浪费仓库分析和增强算力。

**检查维度**:

| # | 维度 | 打回条件 | 原因 |
|---|------|----------|------|
| 1 | 章节 | 正文 < 200 字（去除标题、空行、模板占位符） | 只有标题或一句话，无方案可增强 |
| 2 | 需求可识别性 | Step 5b 提取不到任何具体的功能点或变更点 | proposal 阶段需要明确的“做什么”，否则后续会链路跑偏 |
| 3 | 技术方案存在性 | 无任何技术方案/实现思路/模块设计相关章节 | 纯产品需求文档不是系分，增强无从下手 |
| 4 | 具体性 | 全文无任何类名、模块名、接口名、字段名等具体技术实体 | 还停留在想法阶段，未做任何技术调研 |
| 5 | 模板占位符残留 | 超过 50% 的章节内容为空或仅有占位文字（"请在此处填写"、"TODO"、"待补充"、"xxx"） | 只套了模板没写内容 |

**判定规则**:
- 命中 **2 项及以上** → 打回，终止流程
- 命中 **1 项** → 警告，继续执行

**打回输出**:

```
🔴 系分文档质量不满足增强条件，无法继续。

📄 文档: {doc_title}

缺失项:
  · {具体缺失描述 1}
  · {具体缺失描述 2}

💡 建议:
1. 补充技术方案——至少说明用哪些模块实现、关键类/接口是什么
2. 补充需求细节——明确要做什么功能、涉及哪些场景
3. 完善后重新执行 /acs-tech-design
```

**警告输出**（命中 1 项时）:

```
⚠️ 系分文档存在以下不足，增强效果可能受限：
  · {具体不足描述}

继续执行增强...
```

### Step 7: 仓库深度分析

针对系分文档中提取的每个需求点和技术关键词，在目标仓库中搜索相关上下文。

#### 7a. 知识匹配

复用 `acs-sdd-coding` 阶段 2 Step 2 的语义匹配逻辑：

1. 从 knowledge-index.json 中，对每个 feature 文档（path 不以 `_` 开头）逐条判断与需求的相关性：
   - keywords 与需求领域是否相关
   - title/description 与需求功能是否匹配
2. 匹配到的知识文档加入 `matched_knowledge` 列表
3. 读取每个匹配知识文档的完整内容，提取:
   - **Preferred Entry**（推荐入口）
   - **Avoid Native Or Raw Usage**（禁止直接使用的原生能力）
   - **Import**（导入语句）
   - **Code Example**（代码示例）
   - **Constraints**（约束条件）

#### 7b. 代码模式发现

针对系分文档中的每个需求点执行代码搜索:

**搜索目标**:

| 维度 | 搜索内容 |
|------|----------|
| 入口类 | Manager、Service、Provider、Controller、ViewModel 等与需求相关的类 |
| 现有实现 | 与需求功能相似的已有实现（类名、方法名、模块名） |
| API 风格 | 现有 API 的命名规范、参数风格、返回类型 |
| 数据模型 | 现有 Model/Entity 的定义方式（Codable、Serializable 等） |
| 错误处理 | 项目的错误处理模式（try/catch、Result、error callback） |
| 日志/埋点 | 使用的日志框架、埋点方式、Tag 规范 |

**搜索策略**:
1. 先搜索系分文档中明确提到的类名/模块名/关键词
2. 再搜索相关的封装层、门面类、统一入口
3. 追踪调用关系（从入口到底层实现）
4. 短路规则：某个需求点已找到足够的入口 + 调用模式 + 约束 → 停止搜索该需求点

**搜索工具**: 使用 Grep/Glob 进行精确搜索，使用 Read 读取关键文件，不做全量代码分析。

#### 7c. 约束检测

交叉检查系分文档的技术方案是否与仓库规范冲突：

- 知识文档中标记为 "Avoid" 的原生能力，如果系分文档中使用了 → 标记为需要调整
- 知识文档中的 "Preferred Entry"，如果系分文档未引用 → 标记为建议补充
- Repo Overview 中的架构分层，如果系分文档的设计不一致 → 标记为需要对齐

---

### Step 8: 增强系分文档

保持原有文档结构不变，逐章节注入增强内容。

**增强块格式**:

```markdown
> **[仓库上下文]** <增强内容>
```

**各章节增强规则**:

| 原文档章节类型 | 增强内容 |
|--------------|----------|
| 背景/概述 | 补充: 仓库技术栈上下文（来自 `_repo-overview.md`）、相关模块位置 |
| 需求描述 | 补充: 涉及的具体文件路径、现有类似实现的引用 |
| 技术方案 | 补充: 具体类/文件引用、推荐入口（来自知识文档）、代码模式引用、import 语句 |
| 数据模型 | 补充: 现有 Model 引用、序列化模式 |
| 接口定义 | 补充: 现有 API 风格以保持一致、网络层使用模式 |
| 模块设计 | 补充: 现有模块边界、架构模式对齐建议 |
| 错误处理 | 补充: 项目的错误处理模式、日志规范 |
| 测试用例 | 补充: 测试框架、测试文件位置、现有测试模式 |

**末尾必须追加的全局增强章节**（即使原文档没有对应内容）：

```markdown
## [增强] 关联知识文档

| 知识文档 | 说明 | 关联需求 |
|----------|------|----------|
| <knowledge-name>.md | <description> | <对应的需求点> |

## [增强] 关键代码引用

| 文件路径 | 类/方法 | 作用 | 关联需求 |
|----------|---------|------|----------|
| <relative-path> | <class/method> | <说明> | <对应的需求点> |

## [增强] 推荐实现模式

基于仓库现有代码，建议：
- <模式 1: 说明 + 代码引用>
- <模式 2: 说明 + 代码引用>

## [增强] 潜在风险与约束

- <约束 1: 来自知识文档的禁止项/注意事项>
- <约束 2: 与现有架构的对齐要求>
```

**9b. 输出方式**:

| 选项 | 说明 |
|------|------|
| **写回语雀**（推荐） | 更新原文档内容 |
| **保存为本地文件** | 写入 `<repo_path>/.acs-tmp/tech-design-enhanced.md` |

**写回语雀**:

写回失败 → 自动降级为本地文件保存，告知用户。

**9c. 编码引导**:

输出完成后，提示用户可以使用 acs-sdd-coding 进行编码:

```

   将系分文档转化为代码实现。
```

## Error Handling

| 错误 | 处理 |
|------|------|
| 语雀 URL 无法解析 | 提示检查链接，重试 |
| 文档读取失败 | 重试一次，仍失败则提示提供本地文件 |
| 文档写回失败 | 降级为本地文件保存 |
| 仓库路径不存在 | 报错，重新询问 |
| 分支不存在 | 回退到 master/main，告知用户 |
| Git clone 失败 | 报错，提示替代方式 |
| acs-knowledge-index 未安装 | 警告，降级模式（无知识匹配） |
| 知识索引生成失败 | 警告，继续（无知识匹配） |
| Repo Overview 生成失败 | 警告，继续（上下文减少） |
| 输入质量不达标（≥2 项命中） | 打回终止：列出缺失项和改进建议 |
| 增强文档为空 | 报错终止：未找到可增强内容 |

## Workspace Rules

- 分析阶段对目标仓库**只读**，不修改仓库源代码
- 除 Step 3 的分支切换外，不执行会修改仓库的 git 操作（不 pull/push/commit）
- 临时文件仅写入 `.acs-tmp/` 目录
- 输出需经用户确认后才执行写入
- 原始文档内容不会被删除，只会被追加增强

---

## Quality Bar

增强文档输出前必须满足:

| # | 检查项 | 要求 |
|---|--------|------|
| 1 | 代码引用 | 至少引用 3 个具体且已验证存在的文件路径 |
| 2 | 知识关联 | 至少关联 1 个知识文档（知识索引存在时） |
| 3 | 技术方案增强 | 每个技术方案章节至少有 1 个具体代码引用 |
| 4 | 路径验证 | 所有引用的文件路径必须经 `test -f` 验证存在 |
| 5 | 内容完整 | 增强文档是原始文档的严格增强（不删除任何原始内容） |

达不到质量门槛时:
- 明确告知用户哪些检查项未通过
- 提供 best-effort 结果并标注「低置信度」
