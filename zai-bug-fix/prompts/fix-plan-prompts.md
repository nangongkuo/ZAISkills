# 修复方案展示模板

## 场景1：修复方案展示

```

🔧 修复方案


📌 根因
{根因描述}

📝 修改清单
1. {文件1}:{行号}
   修改前：{原代码}
   修改后：{新代码}

2. {文件2}:{行号}
   修改前：{原代码}
   修改后：{新代码}

📊 影响范围
• 修改文件：{N} 个
• 影响模块：{模块名}
• 复杂度：{simple/medium/complex}

⚠️ 回归风险
• 风险等级：{低/中/高}
• 需验证：{验证场景列表}


```

## 场景2：用户确认选项

```
AskUserQuestion:
  question: "修复方案是否可以？"
  options:
    - label: "方案没问题，开始修复"
      description: "按方案修改代码，进入编码阶段"
    - label: "修改范围需要调整"
      description: "根因对但修改范围需要调整"
    - label: "修复策略需要调整"
      description: "修改方式不对，需要换一种修复策略"
    - label: "回到根因分析"
      description: "根因可能有误，重新分析"
```

## 场景2.1：选「调整范围 / 调整策略」后的提示语

> **触发**：用户在场景2选择「修改范围需要调整」或「修复策略需要调整」后输出。
> **目的**：开放式自由表达，让用户随意说明调整诉求，不限格式。

输出一段提示语，等待用户下一条消息：

```
请说明希望怎么调整，可以提及（都可选，自由发挥）：
  - 必须保留 / 必须修改的文件
  - 禁止修改的文件 / 区域（如稳定模块）
  - 期望的修复方向 / 换一种策略的思路
  - 性能 / 兼容 / 锁 等其他约束
```

**用户回复处理**：

- 收到用户下一条消息后，作为「调整诉求」原文 + 提炼约束写入下面的约束块，作为「附加上下文」喂回 Step 1 重新生成 `fix_plan.md`
- 写入格式建议（N = 当前调整轮次）：

```markdown
## 用户调整诉求（第 N 轮）

{用户原文}

### 提炼约束
- {约束 1}
- {约束 2}
```

- 写入后递增调整轮次计数器，回到 Step 1 重新生成方案 → 重新确认

## 场景3：方案调整后重新确认

```
✅ 修复方案已调整

调整内容:
  • {调整项1}
  • {调整项2}

📝 修改清单（更新后）
1. {文件1}:{行号} - {修改说明}
2. {文件2}:{行号} - {修改说明}



AskUserQuestion:
  question: "更新后的修复方案是否可以？"
  options:
    - label: "方案没问题，开始修复"
      description: "按方案修改代码"
    - label: "继续调整"
      description: "还需要进一步调整"
    - label: "回到根因分析"
      description: "根因可能有误"
```

> 用户选「继续调整」 → **复用场景 2.1 的提示语**，等待下一条用户消息后再写入。

```
⚠️ 已调整 {N}/3 轮

建议基于当前方案继续，或回到根因分析重新审视。

AskUserQuestion:
  question: "如何继续？"
  options:
    - label: "基于当前方案继续"
      description: "进入编码阶段"
    - label: "回到根因分析"
      description: "重新分析根因"
```
