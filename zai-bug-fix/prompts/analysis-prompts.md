# 根因分析结果展示模板

## 场景1：分析结果展示

```

🔍 根因分析结果


📌 疑似根因
{根因描述}

🧾 证据链
commit {hash} → {变更内容} → {引入的问题} → {bug 表现}

📍 涉及代码
• {文件1}:{行号} - {说明}
• {文件2}:{行号} - {说明}

🔧 初步修复方向
{修复策略}

⚠️ 回归风险
{风险评估}


```

## 场景2：用户确认选项

```
AskUserQuestion:
    question: "根因分析结果是否正确？"
    options:
      - label: "根因正确，继续生成修复方案"
        description: "认可当前根因分析，进入修复方案阶段"
      - label: "分析方向有偏差，我补充信息"
        description: "提供更多线索，帮助重新分析"
      - label: "根因不对，需要重新分析"
        description: "当前分析方向错误，重新开始"
```

---

## 场景2.1：选「补充信息 / 重新分析」后的提示语

> **触发**：用户在场景2选择「分析方向有偏差，我补充信息」或「根因不对，需要重新分析」后输出。
> **目的**：开放式自由表达，让用户随意补充线索，不限格式。

输出一段提示语，等待用户下一条消息：

```
请告诉我哪里偏了，可以提及（都可选，自由发挥）：
 - 怀疑的类名 / 方法名 / 文件路径
 - 怀疑的 commit hash 或时间段
 - 复现场景 / 触发条件
 - 其他线索或想说的内容
```

**用户回复处理**：

- 收到用户下一条消息后，作为「补充内容」原文 + 提炼要点写入 `defect_context.md` 的 `## 用户补充（第 N 轮）` 章节（N = 当前分析轮次）
- 写入格式建议：

```markdown
## 用户补充（第 N 轮）

{用户原文}

#### 提炼要点
- {要点 1}
- {要点 2}
```

- 写入后递增分析轮次计数器，回到 Step 1 重新执行

## 场景3：多轮分析提示

```
⚠️ 已分析 {N} 轮，仍未明确定位根因

可能的原因:
1. {可能性1}
2. {可能性2}
3. {可能性3}

AskUserQuestion:
    question: "如何继续？"
    options:
      - label: "基于当前最可能的原因继续"
        description: "选择可能性最高的原因，进入修复方案阶段"
      - label: "我补充更多信息"
        description: "提供更多线索，继续分析"
      - label: "终止分析"
        description: "退出工作流"
```

> 用户在场景3选择「我补充更多信息」 → **复用场景 2.1 的提示语**，等待下一条用户消息后再写入。

## 场景5：代码搜索无结果提示

```
⚠️ 代码搜索未找到相关文件

已尝试的搜索:
- 关键词 "{keyword1}" - 无结果
- 关键词 "{keyword2}" - 无结果
- 模块目录 "{module}" - 未找到

AskUserQuestion:
    question: "未找到相关代码，请提供更多线索"
    options:
      - label: "我提供类名或方法名"
        description: "直接告诉具体的类名或方法名"
      - label: "我提供文件路径"
        description: "直接告诉可能涉及的文件路径"
      - label: "终止分析"
        description: "退出工作流"
```

## 场景6：Commit 分析无相关结果

```
⚠️ 最近 30 条 commit 中未发现明显相关变更

可能原因:
• bug 由更早的变更引入（超过 30 条 commit）
• bug 由配置变更或外部依赖引入
• bug 是一直存在的逻辑问题，非近期引入

将继续基于代码分析进行根因推断...
```
