# 阶段4：编码修复

**目的**：按阶段 3 确认的修复方案修改代码，编译验证。

---

## 输入 Schema

| 字段 | 来源 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| repo_path | state.基本信息.仓库路径 | string | ✅ | 仓库绝对路径 |
| 修复方案路径 | state.阶段3.修复方案路径 | string | ✅ | fix_plan.md 文件路径 |
| 修改文件数 | state.阶段3.修改文件数 | number | ✅ | 需要修改的文件数量 |
| 修复复杂度 | state.阶段3.修复复杂度 | string | ✅ | simple/medium/complex |

---

| 字段 | 写入位置 | 类型 | 说明 |

## 执行步骤

### Step 1：读取修复方案

```
Read <repo_path>/.acs-bug-fix/fix_plan.md
解析修改清单，提取：
  - 每个修改点的文件路径、行号
  - 修改前代码
  - 修改后代码
  - 修改原因
```

---

### Step 2：按修改清单逐项修改代码

**执行逻辑**：

```
for each 修改项 in 修改清单:
  1. Read 目标文件
  2. 定位修改行（根据行号和修改前代码匹配）
  3. 如果行号匹配且修改前代码一致 → 执行替换
  4. 如果行号不匹配 → 用修改前代码内容搜索匹配位置 → 执行替换
  5. 如果修改前代码找不到 → 警告，记录到问题列表，跳过该项
  6. 执行 Edit 替换
```

**约束**：
- 严格按照修复清单执行，不做方案外的额外修改
- 每项修改后检查文件语法（如括号匹配、缩进）
- 如果修改清单中的代码与实际代码不一致（可能文件已被修改），记录差异并尝试智能匹配

---

### Step 3：编译验证

```
调用 acs-build skill 进行编译检查

if 编译通过:
  编译结果 = "success"
  继续 Step 4

if 编译失败:
  编译重试次数 += 1
  if 编译重试次数 <= 5:
    分析编译错误
    if 错误在本次修改范围内:
      修复编译错误
      重新编译
    else:
      警告：编译错误不在本次修改范围内
      记录到问题列表
      尝试修复（仅限明显错误）
      重新编译
  else:
    编译结果 = "failed"
    警告：编译失败，重试已用尽
    记录编译错误到 state.md
    继续 Step 4（不阻塞，由用户决定后续处理）
```

---

### Step 4：代码自查

```
1. 检查修改是否符合修复方案
   → 逐项对比 fix_plan.md 中的修改清单
   → 确认每项修改都已正确应用

2. 检查是否引入新问题
   → 检查修改点周围的代码逻辑
   → 确认没有遗漏的边界条件
   → 确认没有引入新的 null/空值问题

3. 检查编码规范
   → 如果存在知识索引（knowledge-index.json），检查修改是否符合编码规范
   → 如果不存在，跳过此步骤
```

---

|---|--------|----------|------------------|

## 错误处理

| 错误 | 处理 |
|------|------|
| 修改前代码不匹配 | 搜索相似代码，智能匹配；无法匹配则警告并跳过 |
| 编译失败 | 在修改范围内修复，最多重试 5 次 |
| 编译错误不在修改范围内 | 警告，记录到问题列表，尝试修复明显错误 |

---

## 重要约束

- **严格按方案修改**：禁止做修复方案外的额外修改，禁止“顺手重构”
- **编译失败不阻塞**：重试 5 次后仍失败，记录错误继续，由阶段 5 用户确认时决定
- **每项修改可追溯**：所有修改都能在 fix_plan.md 中找到对应项
