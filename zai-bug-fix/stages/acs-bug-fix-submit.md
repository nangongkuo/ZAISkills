# 阶段5：提交代码

**目的**：展示代码变更，用户确认后提交并创建 PR。

---

## 输入 Schema

| 字段 | 来源 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| repo_path | state.基本信息.仓库路径 | string | ✅ | 仓库绝对路径 |
| branch_name | state.基本信息.分支名 | string | ✅ | 当前分支名 |
| 修复方案路径 | state.阶段3.修复方案路径 | string | ✅ | fix_plan.md 文件路径 |
| 根因 | state.阶段2.根因 | string | ✅ | 确认的根因描述 |
| 修改文件列表 | state.阶段4.修改文件列表 | string | ✅ | 实际修改的文件列表 |
| 编译结果 | state.阶段4.编译结果 | string | ✅ | success/failed |
| 无人驾驶 | state.基本信息.无人驾驶 | boolean | ❌ | 是否跳过确认，默认 false |

---

## 输出 Schema

| 字段 | 写入位置 | 类型 | 说明 |
|------|----------|------|------|
| commit_hash | state.阶段5.commit_hash | string | 提交 hash |
| pr_url | state.阶段5.pr_url | string | PR 链接（如果创建） |

---

## 步骤清单

> 开始执行前实例化，每步完成后标记 ✅，输出 `[COMPLETE]` 前逐项确认。

- [ ] Step 1：展示变更 + 用户确认
- [ ] Step 2：提交代码
- [ ] Step 3：创建 PR
- [ ] Step 4：清理状态文件
- [ ] Step 5：结束 Token 监控

---

## 执行步骤

### Step 1：展示变更 + 用户确认

**无人驾驶模式判断**：读取 `state.基本信息.无人驾驶`，若为 `true`，展示变更后直接进入 Step 2。

**正常模式**：

```
1. 执行 git status 查看变更文件
2. 执行 git diff --stat 查看变更统计
3. 展示变更摘要：

📄 变更文件
{文件1} (+{N} -{M})
{文件2} (+{N} -{M})

📊 变更统计
新增 {N} 行，删除 {M} 行，涉及 {K} 个文件

4. AskUserQuestion:
[1] 确认，提交代码
[2] 查看完整 diff
[3] 调整变更（回到阶段 4）
```

- **确认** → 进入 Step 2
- **查看 diff** → 执行 `git diff` 展示完整 diff → 重新确认
- **调整变更** → 回到阶段 4

---

### Step 2：提交代码

```
1. git add 修改的文件（仅 add fix_plan.md 中列出的文件，不 add 其他文件）

2. 生成 commit message:
fix: {缺陷描述关键词摘要}

根因: {根因描述}

修改文件:
- {文件1}: {修改说明}
- {文件2}: {修改说明}

3. git commit
```

---

### Step 3：创建 PR

**无人驾驶模式判断**：读取 `state.基本信息.无人驾驶`，若为 `true`，自动创建 PR。

**正常模式**：

```
AskUserQuestion:
[1] 创建 PR
[2] 稍后手动创建
[3] 自定义 PR 标题
```

- **创建 PR** → 执行 git push + gh pr create（使用默认标题与默认描述）
- **稍后手动** → 跳过 PR 创建
- **自定义标题** → 输出建议标题提示语 → 等待用户下一条消息 → 解析标题与可选描述补充 → 执行 git push + gh pr create

**自定义 PR 标题的提示语**（仅在「自定义 PR 标题」分支输出）：

```
建议标题：fix: {缺陷描述关键词摘要}

如认可建议，回复「用这个」即可；否则直接发送你想要的新标题。
如需补充 PR 描述，可在标题下方空一行后追加（默认描述里已含根因+证据链+修复方案，这里只填想额外补充的内容）。
```

> `{缺陷描述关键词摘要}` 在输出前用 state 中的实际关键词摘要替换。

**用户回复解析**：

- 用户回复「用这个」/「就这个」/「ok」等认可词 → 使用默认建议标题
- 否则取用户消息的**第一行非空文本**作为 `pr_title`
- 若用户消息中包含**空行分隔的后续段落**，整段作为 `pr_extra_desc`；否则 `pr_extra_desc` 为空
- 用户明确放弃自定义 → 回退到默认 PR 标题 + 标准描述（等同于「创建 PR」选项）

**PR 内容**：

```
标题：{pr_title 或默认 "fix: {缺陷描述关键词摘要}"}

描述：
## 根因分析
{根因描述}

## 证据链
{commit → 变更 → 问题 → bug 表现}

## 修复方案
{修改清单摘要}

## 回归验证
{验证场景列表}

{pr_extra_desc 非空时追加:
## 补充说明
{pr_extra_desc}
}
```

### Step 4：清理状态文件

```
删除 <repo_path>/.acs-bug-fix/ 目录
```

---

### Step 5：结束 Token 监控

```
执行命令：
acs-token-monitor end --task "acs-bug-fix" --repo "<repo_path>" --status "success"
```

如遇到任务失败提前终止的情况，执行：
```
acs-token-monitor end --task "acs-bug-fix" --repo "<repo_path>" --status "failure"
```

## 错误处理

| 错误 | 处理 |
|------|------|
| git add 失败 | 检查文件是否存在，重试 |
| git commit 失败 | 检查是否有变更，无变更则跳过 |
| git push 失败 | 检查远程仓库连接，重试 3 次 |
| gh pr create 失败 | 检查 gh 认证状态，提示手动创建 |

---

## 重要约束

- **只提交修复方案中的文件**：禁止 `git add .`，只 add fix_plan.md 中列出的文件
- **commit message 包含根因**：让 PR 审阅者能快速理解修复原因
- **PR 描述包含完整信息**：根因、证据链、修复方案、验证场景
