# 阶段3：修复方案与确认

**目的**：基于阶段 2 确认的根因，生成具体修复方案，用户确认后才进入编码。

---

| 字段 | 来源 | 类型 | 必填 | 说明 |

| 无人驾驶 | state.基本信息.无人驾驶 | boolean | ❌ | 是否跳过确认环节，默认 false |

## 执行步骤

### Step 1：生成修复方案

基于阶段 2 确认的根因，读取相关代码，生成具体修改方案。

**执行逻辑**：

```
1. 读取 defect_context.md 中的根因分析、涉及代码、修复方向
2. 读取涉及代码文件，精确定位需要修改的行
3. 对每个修改点，给出：
   - 修改前代码（精确到行）
   - 修改后代码（精确到行）
   - 修改原因
4. 评估影响范围和回归风险
5. 列出需要验证的场景
```

**输出格式**：

```
🔧 修复方案

📌 根因
{阶段 2 确认的根因}

📝 修改清单
1. {文件1}:{行号}
   修改前：{原代码}
   修改后：{新代码}
   原因：{为什么这样改}

2. {文件2}:{行号}
   修改前：{原代码}
   修改后：{新代码}
   原因：{为什么这样改}

📊 影响范围
• 修改文件：{N} 个
• 影响模块：{模块名}
• 复杂度：{simple/medium/complex}

⚠️ 回归风险
• 风险等级：{低/中/高}
• 需验证：{验证场景列表}
```

### Step 2：用户确认（可迭代）

**无人驾驶模式判断**：读取 `state.基本信息.无人驾驶`，若为 `true`，展示修复方案后直接进入 Step 3。

**正常模式**：展示修复方案，等待用户确认。

**AskUserQuestion**：

按 `prompts/fix-plan-prompts.md` 模板调用 AskUserQuestion：

| 选项 | 含义 | 后续动作 |
|------|------|----------|
| 方案没问题，开始修复 | 用户认可修复方案 | 退出迭代，进入 Step 3 |
| 修改范围需要调整 | 用户认为修改范围不对 | 按场景 2.1 输出提示语 → 等待用户下一条消息 → 按约束重新生成方案 → 重新确认 |
| 修复策略需要调整 | 用户认为修复方式不对 | 按场景 2.1 输出提示语 → 等待用户下一条消息 → 按约束重新生成方案 → 重新确认 |
| 回到根因分析 | 用户认为根因可能有误 | 回到阶段 2 |

**用户选择调整后**：

1. 按 `prompts/fix-plan-prompts.md` 场景 2.1 输出提示语（列出可提及的约束方向，但不强制格式），等待用户下一条消息
2. 收到用户回复后，按场景 2.1 的「写入格式」将原文 + 提炼约束组装成 `## 用户调整诉求（第 N 轮）` 块（N = 当前调整轮次）
3. 把约束块作为「附加上下文」喂回 Step 1 重新生成 `fix_plan.md` → 回到本 Step 重新展示与确认

**迭代保护**：最多 3 轮调整。超过后提示“建议基于当前方案继续，或回到根因分析”。在场景 4 选「继续调整」时，**复用场景 2.1 的自由对话流程**。

---

### Step 3：写入 fix_plan.md

写入 `<仓库路径>/.acs-bug-fix/fix_plan.md`：

```markdown
# 修复方案

## 根因
{确认的根因}

## 证据链
{commit → 变更 → 问题 → bug 表现}

## 修改清单
1. {文件}:{行号} — {修改说明}
   修改前:
   {原代码}

   修改后:
   {新代码}

   原因：{为什么这样改}

## 影响范围
- 修改文件：{N} 个
- 影响模块：{模块名}
- 复杂度：{simple/medium/complex}

## 回归风险
- 风险等级：{低/中/高}
- 需验证场景:
  1. {场景1}
  2. {场景2}
```

## 错误处理

| 错误 | 处理 |
|------|------|
| 代码文件无法读取 | 警告，基于已有信息生成方案 |
| 修改点无法精确定位 | 在方案中标注“待精确定位”，编码阶段要确认 |

---

## 重要约束

- **禁止跳过用户确认**：修复方案必须经用户确认才能进入编码阶段（`checking-skip: true` 无人驾驶模式除外）
- **修改清单必须精确到行**：禁止写“待确认”或“需进一步定位”，编码阶段直接按清单修改
- **最小化修改范围**：修复方案应尽量减少修改文件数和代码行数，不做不必要的重构
- **回归风险必须评估**：每个修复方案必须包含回归风险评估和验证场景
