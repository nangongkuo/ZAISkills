ACS Code Review

# Goal

对代码变更进行系统性审查，产出两类核心价值：

- **风险识别**：发现代码变更中潜藏的不可回滚操作、逻辑缺陷、性能隐患、安全漏洞、兼容性风险和架构违规
- **跨平台一致性**：对比 Android、iOS、HarmonyOS 三端实现，暴露功能缺失、行为分歧和逻辑差异

核心原则：只报真正需要关注的问题，不报噪音。每个发现必须说明影响和修复建议，不泛泛而谈。

# Inputs

一次性展示输入表单，用户填写后直接启动分析，不逐项追问。填几个平台就执行对应模式：1 个平台 = 单平台 CR，2-3 个平台 = 跨平台 CR。

```

--- iOS ---

基准分支/commit: master
目标分支/commit: 10.8.60/develop/cp_masterChange_113700910
```

也支持 commit 对比：

```
--- Android ---
仓库路径：https://code.alipay.com/wallet/android-phone-living-dynamic.git
基准分支/commit: a1b2c3d
目标分支/commit: e5f6g7h
```

### 表单规则

- 每个平台块填了仓库路径即为参与对比，至少填 1 个平台
- 平台块内：填了仓库路径则基准/目标分支也必填；整个平台块留空则不参与
- 基准分支/commit：支持分支名或 commit hash，不猜测 main/master，由用户明确指定
- 目标分支/commit：支持分支名或 commit hash，通常是 feature 分支、版本分支或 commit
- 仓库路径：支持本地路径或 git 远程地址
- 输出路径：用户未指定时使用默认路径，自动创建目录
- 用户可以直接粘贴填写好的表单，或口头说明各字段值

### 审查模式与范围选择（用户确认表单后展示）

用户确认表单后，展示以下选择项：

**审查深度**

默认执行 **完整模式**：
- **Phase 2 单平台风险扫描**：完整执行 A-G 全类别风险扫描
- **Phase 3 跨平台对比**：完整覆盖全部 12 个维度，每个维度都做详细分析

**多平台时的额外选项（2 个及以上平台时展示）**

- **选项 1：仅跨平台差异评审**
- 只分析各平台之间的实现差异
- 输出一份跨平台差异报告

- **选项 2：跨平台差异 + 各单平台内部评审**
- 先对每个平台单独进行风险扫描（Phase 2 单平台 CR）
- 再汇总进行跨平台差异对比（Phase 3 跨平台 CR）
- 输出：各端独立的单平台报告 + 一份汇总跨平台报告

默认推荐：**完整模式**（多平台时）选项 1，用户确认后进入分析流程。

## Workflow

### Phase 1：仓库准备

#### Step 1.1 仓库定位、拉取与分支准备

仓库准备涉及大量标准化 git 操作，**统一通过 CLI 脚本执行**，避免大模型逐步调用 bash 导致效率低下。

**CLI 脚本**：
`acs-code-review/scripts/prepare-repo.sh`

```bash
bash acs-code-review/scripts/prepare-repo.sh "<repo_path>" "<base_ref>" "<head_ref>" "$(pwd)"
```

**脚本职责**：
1. 解析仓库名，定位/创建 `<当前执行目录>/cr-repos/<repo-name>/`
2. 本地不存在则 `git clone`；本地存在则 `git remote -v` 校验 origin URL 并 `fetch`
3. 检查 dirty working tree，存在未提交更改时直接报错
4. 确保基准/目标引用可用（分支则切到最新，commit 则 fetch 验证）
5. 验证 `git log <基准>..<目标>` 范围有效
6. **stdout 最后一行输出仓库根目录绝对路径**

**AI 执行方式**：
- 对每个平台仓库，调用 Bash 工具执行上述脚本命令
- 捕获 stdout 最后一行作为该平台的 **REPO_ROOT**
- 如果脚本 exit code 非 0，将 stderr 内容直接展示给用户，暂停并等待用户处理

**后续所有 git 操作前**，仍需 `cd $REPO_ROOT` 再执行，确保工作目录正确。

#### Step 1.2 批量收集 diff 信息

**统一通过 CLI 脚本执行**，脚本已完成过滤、分类、风险信号扫描、核心 diff 输出。

**CLI 脚本**：`acs-code-review/scripts/collect-diff.sh`

**用法**：
```bash
bash acs-code-review/scripts/collect-diff.sh "$REPO_ROOT" "<base_ref>" "<head_ref>"
```

**输出结构**：

```text
=== STATS ===        # 变更统计
=== COMMITS ===      # commit message 列表
=== CATEGORIES ===   # [core] [test] [config] [resource] [other]
=== RISK SIGNALS === # 按 A/B/C/D/E/F 分类的关键词命中报告
=== CORE DIFFS ===   # 核心文件和配置文件的 diff（已自动截断超大 diff）
```

**AI 执行方式**：
- 对每个平台调用该脚本，捕获完整 stdout
- 跨平台模式下，各平台的脚本调用可以 **并行执行**
- 如果某文件 diff 被截断但对分析至关重要，可单独追加 `git diff <base>..<head> -- file`


### Phase 2：单平台 CR 分析

**执行条件**：
- 单平台模式：**必须执行**
- 跨平台模式 + 用户选择“选项 2（含单平台内部评审）”：对每个平台独立执行
- 跨平台模式 + 用户选择“选项 1（仅跨平台差异）”：**跳过本 Phase**

**执行前准备**：
- **必须先使用 Read 工具读取 `acs-code-review/references/quick-reference.md`**，作为核心判断标准和扫描清单。

#### Step 2.1 提取关键变更摘要

`collect-diff.sh` 输出的 `STATS`、`COMMITS`、`CATEGORIES` 快速理解变更：

1. 从 commit message 提取意图
2. 从 `CORE DIFFS` 和文件分类提炼核心动作（新增功能、修复问题、重构、配置变更等）
3. 识别变更影响的模块/层级
4. 标记变更规模（小/中/大/超大，基于文件数和行数）

#### Step 2.2 风险扫描

`RISK SIGNALS` 作为重点关注方向，但即使某类无信号，也需按 `references/risk-checklist.md` 全量过一遍。

扫描原则：
- 只报有代码证据的问题，不能凭猜测。
- 同类问题合并：同一个文件的多个同类风险合并为一条，列出所有位置。
- 不确定的风险标记为“疑似”并说明不确定性来源。
- 如果代码变更很简单且未发现风险，直接输出“本次变更未发现显著风险”，不强行产出。

#### Step 2.3 风险评级

对每个发现的风险进行评级（标准见 `quick-reference.md`）：

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| P0-Critical | 线上事故风险，必须阻断 | 数据丢失、资金漏洞、Crash |
| P1-High | 高概率影响功能正确性 | 撤销退化、状态卡死、内存泄漏 |
| P2-Medium | 可能影响部分场景 | 边界条件遗漏、性能恶化、兼容性问题 |
| P3-Low | 代码质量改进 | 架构味道、命名不规范、可读性问题 |

#### Step 2.4 生成修复建议

- P0/P1 风险：必须给出具体修复建议（问题描述、影响范围、修复方式、验证方式）
- P2 风险：简要建议
- P3 风险：仅记录



### Phase 3：跨平台 CR 分析（仅在跨平台模式下执行）

**执行前准备**：
- **必须先使用 Read 工具读取 `acs-code-review/references/quick-reference.md`**，了解维度裁剪和差异评估原则。
- **需要先使用 Read 工具读取 `acs-code-review/references/cross-platform-mapping.md`**，作为归一化的详细映射指南。

#### Step 3.1 生成各平台变更归一化描述

对每个平台的变更，生成归一化的功能描述。归一化是指：不使用平台特定的术语和代码概念，而是用业务语义描述要做什么。

**维度处理策略**：
跨平台对比必须覆盖全部 12 个维度，避免漏掉“一端已修复、另一端未修复”的风险。对每个维度都做详细分析。
- **有代码变更的维度**：提取完整的归一化描述
- **无直接代码变更的维度**：追溯两端现有实现，检查是否有一端在已有代码中已存在实现/防护，而另一端在本次变更中仍未补

核心映射逻辑：
1. **功能点识别**：从入口文件追踪调用链，用业务语言命名功能点
2. **逻辑归一化**：对每个功能点，按裁剪后的维度列表提取业务语义描述

> 每个维度的详细描述要求、平台类型映射、特殊场景处理，以 `cross-platform-mapping.md` 为准。

归一化输出格式：

```markdown
## 平台变更归一化描述：[平台名]

### 功能点列表
1. [功能点名称]
- 涉及文件：[文件路径]
- 变更类型：[新增/修改/删除]
- 业务语义：[一句话描述]
- 关键逻辑：[核心判断条件/流程]
- 错误处理：[异常处理方式]
- 依赖接口：[调用的 RPC/服务/模块]
```

#### Step 3.2 跨平台差异对比

将各平台的归一化描述进行逐项对比，识别以下类型的差异：

**A. 功能缺失（Feature Gap）**
- 某个功能点在一个平台实现了，其他平台没有

**B. 行为差异（Behavior Difference）**
- 同一功能在不同平台的行为不同（默认值、触发条件、展示条件等）

**C. 错误处理差异（Error Handling Difference）**
- 同一功能在不同平台的异常处理方式不同（有兜底 vs 无兜底、重试 vs 直接失败等）

**D. 业务逻辑差异（Business Logic Difference）**
- 同一业务规则在不同平台的实现不同（计算公式、条件判断、排序/过滤规则等）

**E. 接口依赖差异（API Dependency Difference）**
- 同一功能在不同平台调用的后端接口不同（参数、接口版本、调用时机等）

**F. 开关/Feature Flag 差异**
- 开关默认值不同、灰度条件不同、生效范围不同
- 一端有开关保护，另一端没有

**G. 埋点/日志差异**
- 埋点事件缺失或触发时机不同
- 埋点参数字段不一致
- 关键转化/错误日志遗漏

**H. 降级/兜底策略差异**
- 异常场景下的兜底内容不同
- 降级恢复逻辑不一致
- 一端有兜底提示，另一端没有

**I. 缓存策略差异**
- 缓存层级/过期策略不同导致数据不一致
- 缓存刷新时机不同
- 一端有缓存一端没有

**J. 超时/重试/并发差异**
- 网络超时时间不一致
- 重试次数/退避策略不同
- 请求取消/并发限制逻辑不一致

**K. 安全/权限差异**
- 权限申请时机或申请方式不同
- 敏感数据处理方式不一致
- 鉴权/Token 刷新机制不同

**L. 性能/加载策略差异**
- 预加载/懒加载触发条件不同
- 图片/资源压缩降级策略不一致
- 渲染优化（骨架屏、局部刷新）缺失

#### Step 3.3 差异严重度评估

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| P0-Critical | 三端存在导致线上事故的差异 | 另一端忘记拦截、一端有数据丢失风险，另一端忘记防护 |
| P1-High | 功能缺失或核心流程不一致，影响用户体验 | A 平台有某功能，B 平台缺失 |
| P2-Medium | 行为差异或错误处理差异，可能影响部分场景 | 两端默认值不同、兜底体验不同 |


评估原则：
- 差异判断必须基于归一化后的业务语义，不能只看代码表面。
- 功能缺失判断必须谨慎；某端未实现可能是有意为之（如平台不支持、策略差异），需标记原因。
- 只对比本次变更涉及的范围内差异，不做全局一致性审查。

#### Step 3.4 生成对齐建议

对 P0/P1 差异给出对齐建议：差异描述、影响分析、建议对齐方向、需修改的平台和预估改动范围。



### Phase 4：输出审查结果

#### Step 4.1 生成报告内容

按用户选择，输出内容：

- 单平台：1 份单平台报告（按 `acs-code-review/references/output-template-single.md`）
- 跨平台选项 1（仅跨平台差异）：1 份跨平台汇总报告（按 `acs-code-review/references/output-template-cross.md`）


执行前请 **先使用 Read 工具读取对应的输出模板文件**。

#### Step 4.2 写入报告文件

- 单平台模式 / 跨平台选项 1：写入用户确认的输出路径
- 跨平台选项 2：各单平台报告写入 `<输出目录>/<平台>-<YYYYMMDD-HHmm>.md`，跨平台汇总报告写入 `<输出目录>/cross-<YYYYMMDD-HHmm>.md`

#### Step 4.3 对话内汇报
```
写入完成后，在对话中按以下格式向用户汇报：


**审查结论**：[可合入/需修复后合入/需对齐差异后合入]

**报告文件**：
- <文件路径1>
- <文件路径2>（如有）

**风险/差异概要**：
- [单平台 / Android] P0: N, P1: N, P2: N, P3: M
- [单平台 / iOS] P0: N, P1: N, P2: N, P3: N
- [跨平台] P0: N, P1: N, P2: N, P3: M

**关键发现（P0/P1）**：
1. [文件：行号] <描述> - <修复/对齐建议>
2. [文件：行号] <描述> - <修复/对齐建议>

> 完整报告已写入上述文件，请打开查看详细内容。
```

如果未发现 P0/P1 风险，对话中直接说明“本次变更未发现 P0/P1 级别风险”即可，无需罗列 P2/P3。



# Output Rules

- 每个风险/差异必须包含：描述、严重级别、文件路径、行号（如能定位）
- P0 和 P1 必须给出修复/对齐建议
- 不报无意义的发现：注释中的拼写错误不算风险，格式偏好不算架构违规
- 同类问题合并：同一个文件的多个同类风险合并为一条，列出所有位置
- 全文控制在可一屏阅读的长度，不产出一万字报告
- 使用中文输出
- 如果代码变更很简单且未发现风险，直接输出“本次变更未发现显著风险”，不强行产出

# Quality Bar

### 风险发现门槛

- 每个风险必须有明确的代码证据（diff 中的具体行），不能只凭“可能有”
- P0/P1 风险必须有可验证的触发条件描述
- 不确定的风险标记为“疑似”并说明不确定性来源
- 如果代码变更很简单且未发现风险，直接输出“本次变更未发现显著风险”，不强行产出

### 跨平台对比门槛

- 差异判断必须基于归一化后的业务语义，不能只看代码表面
- 功能缺失判断必须谨慎：某端未实现可能是有意为之（如平台不支持），需要标记
- 只对比本次变更涉及的范围内差异，不做全局一致性审查

### 整体质量

- 不漏报 P0 风险：宁可多报疑似 P0，不可漏报
- 修复建议必须具体，不能只说“需要修复”

# Workspace Rules

- 仓库代码只读，不做代码修改（CR 报告文件除外）
- 不执行 git 写操作（commit/push），但允许 checkout 切换分支和 pull 拉取
- 远程仓库不在本地时，通过 antcode skill 拉取
- 跨平台模式下，各仓库代码只读，不跨仓库写入
- CR 报告写入用户确认的输出路径，默认在当前执行目录下 `cr-reports/` 目录
- 大型 diff（超过 200 个文件变更）应提醒用户缩小范围
